## Конфигурация

Все настройки — в `appsettings.json`; любую можно переопределить переменной окружения (двойное подчёркивание вместо двоеточия: `Auth__ApiKey`, `Probe__MaxParallel`).

### Сервер (`SPI.Twamp.Server/appsettings.json`)

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `Urls` | `http://0.0.0.0:9000` | адрес и порт HTTP |
| `Database:Path` | `TWamp.db` | путь к файлу LiteDB |
| `Database:CheckpointMin` | `5` | период переноса WAL-журнала (`*-log.db`) в основную базу |
| `Auth:ApiKey` | *(пусто)* | общий ключ API; пусто — аутентификация выключена |
| `Probe:HttpTimeoutSec` | `60` | таймаут HTTP-запросов к пробам (включая длинный опрос) |
| `Probe:ReconcileIntervalSec` | `30` | период фоновой сверки задач с пробами |
| `Probe:CleanupWaitHours` | `24` | сколько **часов** после удаления пробы ждать её появления, чтобы снять с неё задания; по истечении — задачи пробы и кэш вычищаются |
| `Retention:IntervalMin` | `60` | период запуска очистки БД |
| `Retention:RawDays` | `14` | хранение сырых результатов, дней (**только для данных, накопленных до перехода на ClickHouse**) |
| `Retention:StatsDays` | `90` | хранение разобранной статистики, дней (**то же — историческая уборка**) |
| `Retention:DeletedTaskDays` | `7` | через сколько дней окончательно вычищать удалённые задачи |

#### Выгрузка результатов в ClickHouse

Результаты зондирования **не хранятся в базе сервера**: они складываются в дисковый буфер
и переносятся в ClickHouse, после чего файл буфера удаляется. Подробнее — [архитектура](architecture.md#путь-результатов-в-clickhouse).

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `ClickHouse:Enabled` | `false` | включает перенос результатов в ClickHouse |
| `ClickHouse:Url` | `http://localhost:8123` | адрес HTTP-интерфейса ClickHouse |
| `ClickHouse:Database` | `twamp` | база (создаётся автоматически) |
| `ClickHouse:Table` | `results` | таблица (создаётся автоматически) |
| `ClickHouse:User` / `ClickHouse:Password` | `default` / *(пусто)* | учётные данные |
| `ClickHouse:BatchRows` | `100000` | **сколько строк** копится в сегменте, прежде чем он уйдёт в базу |
| `ClickHouse:FlushMinutes` | `10` | **через сколько минут** сегмент уходит в базу, даже если строк меньше |
| `ClickHouse:MaxSegments` | `16` | **сколько сегментов** накопить при недоступности базы, прежде чем приостановить опрос проб |
| `ClickHouse:SpoolPath` | `spool` | каталог буфера (относительный — от папки приложения) |
| `ClickHouse:RetrySeconds` | `30` | пауза перед повтором после ошибки базы |
| `ClickHouse:TimeoutSec` | `300` | таймаут HTTP-запроса к базе (вставка большого сегмента идёт долго) |

Порог `BatchRows` × `MaxSegments` задаёт ёмкость буфера: при значениях по умолчанию сервер
переживает недоступность ClickHouse, накопив до 1 600 000 строк. Дальше опрос проб
приостанавливается, и результаты ждут **на пробах** (у них своя очередь, см. `Probe:MaxPendingResults`) —
ничего не теряется, пока база не вернётся.

### Проба (`appsettings.json` рядом с `twamp-probe`)

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `Urls` | `http://0.0.0.0:8443` | адрес и порт HTTP |
| `Auth:ApiKey` | *(пусто)* | тот же ключ, что на сервере |
| `Probe:MaxParallel` | `100000` | **сколько замеров идёт одновременно** (пул воркеров). Значение берётся как есть: проба **не урезает** его ни под число ядер, ни под лимиты системы. Это верхняя граница, а не план — фактический предел снижается, когда кончается память (см. ниже). `0` означает значение по умолчанию |
| `Probe:MinParallel` | `16` | нижняя граница: ниже этого предел не опускается даже при полной нехватке памяти — замеры продолжаются |
| `Probe:StartParallel` | `64` | **с какого предела проба начинает после запуска** — дальше разгоняется, сверяясь с памятью |
| `Probe:MemoryHighPercent` | `95` | занятость памяти, выше которой предел **режется вдвое** немедленно |
| `Probe:MemoryLowPercent` | `80` | занятость памяти, ниже которой разрешён **разгон** предела |
| `Probe:MemoryCheckSec` | `5` | период проверки памяти (`0` — слежение выключено, предел фиксирован) |
| `Probe:MaxPendingResults` | `100000` | лимит очереди **результатов** при недоступности сервера (старые вытесняются) |
| `Probe:QueueCapacity` | `100000` | ёмкость очереди **задач** диспетчера — сколько сработавших задач ждут свободного воркера. Это **не** число одновременных замеров (его задаёт `MaxParallel`) и не очередь результатов: держать её заметно больше числа воркеров нормально — запас нужен, чтобы постановка не блокировала приём HTTP при массовой заливке. В журнале запуска все три величины видны отдельно: `воркеров`, `очередь_задач`, `очередь_результатов` |
| `Probe:PortRange` | `20000-32767` | **диапазон локальных портов, которые проба раздаёт зондам сама**. Два замера не могут взять один порт, а когда свободных нет — замер **ждёт освобождения**, вместо того чтобы упасть с «address already in use». Пул общий для TWamp и TWampy — за номера они не конкурируют. Порт выдаётся в аренду: после возврата он секунду отлёживается и встаёт в конец очереди, поэтому номера идут по кругу, а хвосты прошлого замера не попадают в следующий (под нагрузкой срок уступает — недолежавший порт лучше очереди замеров). Порт, занятый чужим процессом, уходит в **карантин на 5 минут**, а замер повторяется с другим номером (до десяти попыток); по истечении карантина порт возвращается в оборот сам. **Диапазон обязан быть зарезервирован в ядре** (`net.ipv4.ip_local_reserved_ports` в `99-twamp-probe.conf`) — иначе расширенный эфемерный диапазон накроет пул, и ядро отдаст наши порты чужим соединениям. Пусто — порт выбирает ядро, как раньше. Алгоритм целиком — [здесь](parallelism.md#как-проба-выбирает-локальные-порты) |
| `Probe:PersistIntervalSec` | `5` | период сохранения очереди недоставленных результатов на диск (больше — меньше дисковая нагрузка; при аварии теряется максимум этот интервал; при штатной остановке — финальный снимок) |
| `Probe:ServerTimeoutHours` | `24` | сторож связи: если сервер не обращался к пробе дольше этого числа **часов**, проба считает себя удалённой — останавливает все задачи и чистит реестр с кэшем (0 — выключено) |
| `ping:name` | `ping` | исполняемый файл для режима WinPing |
| `twamp:name` | `./twping` | исполняемый файл `twping` (perfsonar) для режима TWamp. В linux-пакете пробы `twping` **уже лежит рядом** — из релизного пакета perfSONAR для el7, поэтому работает начиная с CentOS 7 (нужна только системная `libcap`, она есть везде с systemd) |
| `twamp:embedded` | `false` | **выполнять TWamp встроенным клиентом**, прямо в процессе пробы. Внешняя утилита не запускается, поэтому замер не занимает ни процесса, ни потока ожидания — предел одновременных замеров на него **не распространяется** (см. [Сколько замеров одновременно](parallelism.md)). Используется библиотека [twping-go](https://github.com/akprof2000/twping-go) — та же, из которой собрана сама утилита |
| `twampy:name` | `python3` | интерпретатор Python; проба запускает `python3 -m twampy …` (см. [Как работать с TWampy](twampy.md#как-работать-с-twampy)) |
| `twampy:embedded` | `false` | **выполнять TWampy встроенным отправителем**, прямо в процессе пробы. Python не нужен вовсе, а замер не занимает ни процесса, ни потока ожидания — предел одновременных замеров на него **не распространяется** (см. [Сколько замеров одновременно](parallelism.md)) |
| `ping:default` / `twamp:default` / `twampy:default` | *(пусто)* | аргументы по умолчанию, если у задачи нет своих |

> **Лимиты ОС проба проверяет, но настройку не меняет.** Подробный разбор —
> в отдельной статье [«Сколько замеров можно запускать одновременно»](parallelism.md);
> здесь — самое главное.
>
> Один замер **внешней утилитой** стоит ядру двух учётных единиц: процесса зонда
> и потока пробы, который ждёт его завершения (замер: на 1500 зондов у пробы
> 1523 потока). Обе считаются в одном лимите `ulimit -u` (`RLIMIT_NPROC`).
> Когда он исчерпан, Go не может создать поток и падает с **fatal error** — это
> не паника, перехватить её нельзя, служба умирает целиком.
>
> Типовая настройка CentOS/RHEL — `ulimit -u = 4096` (файл
> `/etc/security/limits.d/20-nproc.conf`), то есть всего **2048 одновременных
> замеров** внешними утилитами. Проба это заметит и предупредит при старте,
> но настройку оставит вашей:
>
> ```
> WARN Система может не выдержать настроенное число замеров настроено=100000
>      причина="лимит процессов и потоков пользователя (ulimit -u) = 4096,
>      а на 100000 одновременных замеров внешними утилитами нужно ~200000…"
> ```
>
> Что проба поднимает сама: мягкий `ulimit -u` до жёсткого и предел потоков Go
> (по умолчанию 10000 — без подъёма настройка выше упёрлась бы в него).
> Что поднять можете только вы — лимиты службы и ядра:
>
> ```ini
> [Service]
> LimitNPROC=65535
> LimitNOFILE=1048576
> ```
>
> На **встроенные зонды** (`twamp:embedded`, `twampy:embedded`) всё это не
> распространяется: они не занимают ни процесса, ни потока.
>
> **Подбор `Probe:MaxParallel`.** По умолчанию 100000 — заведомо больше любой
> практической нагрузки, чтобы настройка не мешала. Ограничивать её имеет смысл
> в одном случае: **короткие CPU-активные зонды** (`ping -n 1`), где большое
> значение просто насыщает процессор — ориентир `4 × число ядер` (на 16 ядрах 64
> обрабатывает 10 000 задач быстрее, чем 200 — см. [Производительность](#производительность)).
> Для длинных I/O-замеров TWAMP (`twping -c 300 -i 1` живёт ~5 минут и почти
> спит) уменьшать значение не нужно: фактический предел всё равно определяется
> памятью.
>
> **Предел сам подстраивается под память.** `MaxParallel` — это потолок, а не постоянная
> величина. Каждый зонд — отдельный процесс (`python3 -m twampy` занимает 15–25 МБ), поэтому
> на пике из тысяч задач упирается не процессор, а память: ядро начинает отказывать в запуске
> с `fork/exec: cannot allocate memory`, и замеры пропадают. Чтобы этого не происходило,
> проба следит за занятостью памяти и меняет фактический предел:
>
> **Проба не запускает всё разом.** После старта предел равен `StartParallel` (64), и проба
> наращивает его, сверяясь с памятью, — «медленный старт». Иначе тысячи задач с одинаковым
> cron срываются одновременно и съедают память раньше, чем сработает первая её проверка.
>
> | Условие | Что делает проба |
> |---|---|
> | занятость выше `MemoryHighPercent` (95%) | снижает предел **вдвое** немедленно |
> | запущенные зонды съели **больше половины** свободной памяти | снижает предел **вдвое** |
> | **предел не выбран** — свободные слоты есть | **не трогает предел** |
> | **предыдущая пачка ещё осваивается** — зонды запускаются или память заметно убывает | **ждёт следующей проверки** |
> | предел выбран, пачка освоилась, упора ещё не было | **разгон**: удваивает предел |
> | предел выбран, пачка освоилась, но упор уже был | **плавно**: прибавляет четверть |
>
> Всё решение строится вокруг **реально запущенных зондов**, а не вокруг самого
> числа-предела: предел — это лишь разрешение, память тратят процессы. Отсюда два правила.
>
> **Расход считается на прирост работающих зондов** и даёт цену одного зонда. По ней
> прибавка урезается до того, что физически влезает в свободную память (на прибавку
> отводится не больше половины свободного — остальное запас: память освобождается
> с задержкой, да и соседние службы никуда не делись).
>
> **После каждого изменения предела проба ждёт, пока пачка освоится.** Запуски
> разворачиваются не мгновенно, и память процессы отбирают с задержкой. Менять
> предел в этот момент — значит решать по недосчитанному расходу: проба увидела бы
> «дёшево» и удвоилась ещё раз, а настоящая цена предыдущего шага пришла бы после.
> Поэтому следующего шага не будет, пока не сойдутся два признака: зонды перестали
> прибавляться **и** потребление выросло незначительно (убыль свободной памяти
> меньше ~6% от неё). Пока потребление заметно растёт — ждём ещё одну проверку.
> Аварийное сжатие при нехватке памяти этой паузы не ждёт — это защита, она срочная.
>
> **Предел растёт, только когда он выбран до конца** — то есть зонды упираются в него
> и ждут слот. Поднимать потолок, под которым работает три задачи из сотни, бессмысленно:
> нагрузки это не добавит, а замер расхода испортит — память в этот момент меняют
> посторонние службы. Без этого правила проба «разгонялась» бы вхолостую на простое
> до значения, которое первая же настоящая пачка задач обращает в отказ по памяти.
>
> Одной лишь занятости мало: при 64 ГБ всего и 16 ГБ свободных занято 75% — формально
> «запас есть», а следующее удвоение уже не влезет. Расход показывает это на шаг раньше.
> Разгон под нагрузкой выглядит так (память 64 ГБ):
>
> ```
> 16 зондов  → съели 2 ГБ из 64  → предел 32     дёшево, разгон
> 32 зонда   → съели 14 ГБ из 62 → предел 64     меньше половины, разгон
> 64 зонда   → съели 8 ГБ из 48  → предел 128    дёшево, разгон
> 128 зондов → съели 24 ГБ из 40 → предел вдвое вниз, вместо гибельного 256
> ```
>
> После упора две ближайшие проверки пропускаются: процессы завершаются не мгновенно,
> память освобождается с задержкой. Каждое изменение предела попадает в журнал с причиной,
> объёмами памяти, измеренной ценой зонда и новым значением.

> **Повторный запуск задачи не накапливается.** Если предыдущий замер задачи ещё идёт
> (`twping -c 300` живёт минутами, а расписание может сработать раньше), новое срабатывание
> **пропускается** с записью в журнал — иначе запуски одной задачи копились бы и съедали память.

> **Отладка на Windows без TWping**: задайте `twamp__name=ping` через переменную окружения (или поменяйте `twamp:name` в конфиге) — задачи TWamp будут выполняться системным ping. Если исполняемый файл зонда не найден, ошибка «Не удалось запустить зонд…» видна в статусе задач пробы и в отчёте.

## Безопасность

- Задайте **одинаковый** ключ в `Auth:ApiKey` сервера и всех проб (или `Auth__ApiKey` через окружение). Пустой ключ = аутентификация выключена (допустимо только в изолированной сети).
- Все запросы к `/api/**` требуют заголовок `X-Api-Key`; веб-интерфейс и Swagger остаются доступны (UI сам передаёт ключ).
- Сервер автоматически подписывает ключом все запросы к пробам.

> Проба исполняет команды ОС по указанию сервера — не оставляйте её без ключа в недоверенной сети.

## Производительность

Замеры на 16-ядерной машине (проба и сервер локально):

| Сценарий | Результат |
|---|---|
| 10 000 задач одним `SetJobs` | приняты без зависаний, веб-интерфейс отвечает |
| 10 000 ping-задач, `MaxParallel=64` | все выполнены за ~24 с (~420 результатов/с) |
| Массовая заливка 2 000 задач (1000 роутеров × 2 шаблона) | доставка пробе за ~5 с двумя пачками |
| Сквозная доставка 505 задач сервер→проба→сервер | 504/505 результатов в БД (1 потерян только при одновременном kill обеих служб — до внедрения ACK; с ACK потери исключены) |

Ключевые решения: неблокирующий длинный опрос (Channel вместо блокировки потока), пул воркеров вместо неограниченного `Task.Run`, пакетная доставка задач, разбор статистики при приёме, потоковая выгрузка отчётов.

### Дисковая нагрузка пробы

Проба спроектирована так, чтобы писать на диск минимально:

- очередь недоставленных результатов сохраняется **снимком по таймеру** (`Probe:PersistIntervalSec`, по умолчанию 5 с) и только при наличии изменений — не на каждый результат и не на каждую выдачу/подтверждение пачки; при штатной остановке делается финальный снимок;
- если сервер долго недоступен и очередь разрослась, интервал сохранения **автоматически растягивается** (средняя скорость записи снимков ограничена ~10 МБ/с) — гигантский файл не переписывается впустую;
- файловые логи пишутся с уровня **Info** (Debug-поток тысяч зондов идёт только в консоль с ограничителем), файл лога держится открытым, записи буферизуются асинхронной обёрткой.
