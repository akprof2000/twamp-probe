## Как работать с TWampy

В проекте **два** независимых TWAMP-инструмента, и оба доступны как режимы задачи:

| Режим | Утилита | Что это |
|---|---|---|
| `TWamp` | `twping` | клиент TWAMP от [perfsonar](https://github.com/perfsonar) (полный TWAMP с TCP-контролем) |
| `TWampy` | `twampy` | [nokia/twampy](https://github.com/nokia/twampy) — TWAMP-Light на Python, **вендорен в репозитории** (`SPI.TWamp.Probe/twampy/`) |

### Зачем отдельный TWampy и почему форк

Оригинальный twampy-sender биндит фиксированный локальный UDP-порт (`:20000`), поэтому
**второй параллельный запуск падает** — под нагрузку на 10 000 задач это неприменимо.
В форке дефолт локального порта изменён на **эфемерный (`:0`)**: ОС выдаёт каждому
отправителю свободный порт, и тысячи процессов работают одновременно без конфликтов
(TWAMP-Light не ведёт TCP-переговоры, поэтому фиксированный порт не нужен). Рефлектор
отражает на адрес источника, так что эфемерный порт корректно принимает ответ.

### Что изменено в форке относительно nokia/twampy

Два изменения, оба в отправителе (`TwampySessionSender.run`). Всё остальное — формулы
задержек, джиттер [RFC1889], подсчёт потерь, формат таблицы — оставлено как в оригинале,
поэтому значения сходятся с базовой версией (замеры ниже).

| Что | Зачем | Эффект |
|---|---|---|
| Локальный порт по умолчанию `:0` вместо `:20000` | оригинал биндит фиксированный порт, поэтому **второй параллельный запуск падает** | тысячи отправителей работают одновременно |
| Убран холостой цикл ожидания (busy-wait) | блокирующее ожидание стояло **только внутри ветки отправки пакета**, поэтому цикл крутился вхолостую: когда ответ приходил раньше следующего слота (на нормальной сети — всегда) и после отправки последнего пакета (до 5 секунд подряд) | расход процессора меньше в десятки раз |

Как именно убран busy-wait — в цикле появилась **единственная точка ожидания**: сон на
сокете до ближайшего события (следующий слот отправки, а когда всё отправлено — истечение
времени ожидания ответов). Плюс ранний выход, когда все ответы уже получены: иначе сессия
досыпала до конца таймаута уже после завершения замера (это стоило +5 секунд на каждый замер).

Диф с оригиналом по циклу отправителя — 7 добавленных строк и 2 убранных:

```python
+ if not self.running:                       # все ответы получены — выходим сразу
+     break
+ deadline = schedule if idx < self.count else endtime
+ timeout = deadline - now()
+ if timeout > 0:
+     select.select([self.socket], [], [], timeout)   # единственная точка ожидания
- if schedule > t1:                                    # было: ожидание только при отправке
-     r, w, e = select.select([self.socket], [], [], schedule - t1)
```

### Измерения: до и после

**Расход процессора** — замер `-c 300 -i 100` (300 пакетов с интервалом 100 мс, ~30 секунд):

| Платформа | Было (оригинал) | Стало (форк) | Разница |
|---|---|---|---|
| Linux (контейнер `python:3.12`) | **28.38 c** CPU | **0.33 c** CPU | в **86 раз** меньше |
| Windows | **29.47 c** CPU, 97.5% ядра | **0.52 c** CPU, 1.7% ядра | в **57 раз** меньше |

То есть раньше один замер занимал ядро почти целиком всё время своей работы; при сотнях
одновременных задач это и было причиной высокой нагрузки на пробу.

**Значения замеров** — они обязаны совпадать с оригиналом. Проверка на рефлекторе с
имитацией сетевой задержки 5 мс (`-c 50 -i 20`, 5 прогонов, Roundtrip Avg):

| Версия | Прогоны | Среднее | Потери |
|---|---|---|---|
| оригинал nokia | 5.61 / 5.71 / 5.66 / 5.71 / 5.64 мс | **5.67 мс** | 0.0% |
| наш форк | 5.81 / 5.73 / 5.78 / 5.67 / 5.66 мс | **5.73 мс** | 0.0% |

Расхождение ~1% — в пределах разброса самих прогонов.

> **Как правильно сравнивать.** На петлевом интерфейсе (`127.0.0.1`, RTT ~0.2–0.4 мс) форк
> показывает **бо́льшие** значения, чем оригинал (около 0.6 мс против 0.35 мс). Это не ошибка
> измерения, а артефакт методики: оригинал крутит busy-spin и забирает ответ мгновенно, а форк
> спит на сокете и просыпается с задержкой планировщика ОС (~0.2–0.3 мс). На петле эта задержка
> сопоставима с измеряемой величиной, на реальной сети (единицы-десятки миллисекунд) теряется
> в шуме. Поэтому сверять версии нужно на реалистичной задержке, а не на localhost.

**Параллельная работа и целостность данных:**

| Проверка | Результат |
|---|---|
| 100 одновременных отправителей против флота рефлекторов | 100/100 успешных, потери 0.0%, за 3.6 с |
| Залп 500 задач через сервер на одну пробу | приняты и выполнены, 500/500 |
| Сквозной прогон: проба → сервер → отчёт | **1014 задач → 1014 результатов → 1014 строк**, потерь данных нет, ошибок 0 |

### Как проба запускает twampy

Пакет twampy копируется в вывод сборки пробы (папка `twampy/` рядом с исполняемым файлом).
Проба вызывает его через интерпретатор Python:

```
python3 -m twampy sender <адрес-рефлектора> <аргументы задачи>
```

- `<адрес-рефлектора>` — цель зондирования (`EndNode` задачи), подставляет проба;
- локальный порт **эфемерный** (`:0`) — в форке это значение по умолчанию, отдельно указывать не нужно;
- `<аргументы задачи>` — из поля `Request` шаблона/задачи (например `-c 300 -i 100`).

#### Формы вызова

Все варианты рабочие (проверено, потери 0%), но для параллельной работы годятся не все:

| Вызов | Локальный порт | Годится для параллельной работы |
|---|---|---|
| `sender 10.0.0.5:20001 -c 10 -i 100` | эфемерный (подставляется сам) | ✅ да — **так вызывает проба** |
| `sender 10.0.0.5:20001 :0 -c 10 -i 100` | эфемерный (указан явно) | ✅ да |
| `sender 10.0.0.5:20001 10.0.0.9:0 -c 10` | эфемерный, но **с конкретного интерфейса** | ✅ да |
| `sender 10.0.0.5:20001 :31000 -c 10` | фиксированный `31000` | ❌ **нет** |
| `sender 10.0.0.5:20001 10.0.0.9:31000 -c 10` | фиксированный интерфейс и порт | ❌ **нет** |

> **Не задавайте локальный порт в параметрах задачи.** Проверка: 5 одновременных отправителей
> с фиксированным `:31000` — выжили только 2 из 5 (остальные не смогли занять уже занятый порт);
> те же 5 без указания локального порта — **5 из 5** успешно. Локальный порт нужен ровно
> для того, чтобы принять ответ, и его значение ни на что не влияет — отдавайте его ОС.

> **Замер с конкретного интерфейса.** Если на пробе несколько интерфейсов и замер должен
> уходить строго с нужного (например, с сервисного адреса, который знает рефлектор), задайте
> near-end **первым параметром задачи**, оставив порт нулевым:
>
> | Поле задачи | Значение |
> |---|---|
> | `EndNode` (узел) | `10.0.0.5:20001` — рефлектор |
> | `Request` (параметры) | `10.0.0.9:0 -c 10` — локальный адрес, затем опции |
>
> Проба соберёт `python3 -m twampy sender 10.0.0.5:20001 10.0.0.9:0 -c 10`: первый позиционный
> аргумент — far-end, второй — near-end. Интерфейс фиксирован, порт остаётся эфемерным,
> поэтому параллельность не страдает.

#### Параметры, которые понимает twampy

| Параметр | Назначение |
|---|---|
| `-c`, `--count` | число пакетов |
| `-i`, `--interval` | интервал между пакетами, **мс** |
| `--padding` | размер набивки пакета, байт |
| `--tos` / `--dscp` | поле TOS / DSCP в IP-заголовке |
| `--ttl` | TTL |
| `--do-not-fragment` | запрет фрагментации |
| `-q` / `-v` / `-d` | тише / подробнее / отладка |

> **Параметры twping и twampy не взаимозаменяемы.** Если в задаче режима `TWampy` оставить
> набор от twping (например `-c 300 -i 1 -b 0.000001 -D 46 -s 224`), запуск завершится ошибкой
> `unrecognized arguments: -b 0.000001 -D 46 -s 224`, и это попадёт в отчёт как ошибочный замер.
> Соответствие: `-D 46` (DSCP у twping) → `--dscp 46`, `-s 224` (размер) → `--padding 224`,
> аналога `-b` (полоса) у twampy нет — темп задаётся через `-i`.

> **Важно про `twampy:name`.** Это **только интерпретатор** — часть `-m twampy sender …`
> проба подставляет сама. В конфиге пишите ровно `python3` (Windows — `python`):
>
> | Значение `twampy:name` | |
> |---|---|
> | `python3` / `python` | ✅ правильно |
> | `python3 -m twampy` | ❌ попадёт в имя исполняемого файла целиком — запуск упадёт |
> | `./twampy` | ❌ такого файла нет (twampy — Python-пакет, а не бинарник) |

Требования на пробе: **Python 3.8+** в `PATH`. Отдельно ставить twampy не нужно — он уже
в поставке, `pip install` не требуется (только stdlib). Пакет находится по `sys.path`:
проба добавляет свой каталог приложения в `PYTHONPATH` дочернего процесса, поэтому запуск
не зависит от рабочего каталога службы (в т.ч. под systemd — `WorkingDirectory` указывать необязательно).

Рефлектор (отражатель) на целевом узле поднимается тем же пакетом:

```
python3 -m twampy responder :20001          # один порт
python3 -m twampy responder-fleet :20001 --count 10000   # массовый режим форка (нагрузочный тест)
```

### Сходимость значений с TWamp

twampy печатает таблицу `Outbound / Inbound / Roundtrip` × `Min / Max / Avg / Jitter / Loss`
(значения с единицами us/ms/sec/min). Парсер [`TwampyParser`](../SPI.Twamp.Server/Parser/TwampyParser.cs)
приводит её к **тем же полям `TwPingStats`**, что и вывод twping:

| twampy | → | TwPingStats (как у twping) |
|---|---|---|
| Roundtrip Min / Avg / Max | → | `RttMin` / `RttMedian` / `RttMax` |
| Roundtrip Jitter / Loss | → | `TwoWayJitter` / `LossPercent` |
| Outbound Min/Avg/Max/Jitter | → | `SendMin/Median/Max` / `SendJitter` |
| Inbound Min/Avg/Max/Jitter | → | `ReflectMin/Median/Max` / `ReflectJitter` |

Единицы нормализуются в **миллисекунды**; `NO STATS AVAILABLE (100% loss)` → `LossPercent = 100`.
Парсер выбирается по режиму задачи в [`ProbeOutputParser`](../SPI.Twamp.Server/Parser/ProbeOutputParser.cs).
Поэтому в отчёте, БД и веб-интерфейсе данные TWampy и TWamp **неотличимы по смыслу** —
колонка `Mode` лишь указывает, какой утилитой сделан замер.

> Массовый форк для нагрузочного теста (тысячи рефлекторов/отправителей в одном процессе)
> живёт в отдельном репозитории `twampy-fleet`; в пробу вендорены те же файлы с правкой
> эфемерного порта.
