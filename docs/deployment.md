Для установки на три узла ClickHouse и две машины съёма используйте [кластерный профиль и порядок миграции](../deploy/ha/README.md).

## Переход на три службы

1. Остановите прежний центральный сервер. Сохраните его `TWamp.db`, каталог `spool`, настройки, а на пробах — файлы состояния. Старый процесс мог отправлять ACK сразу после записи в собственный буфер.
2. Обновите конфигуратор в прежнем каталоге. Он продолжит использовать существующую LiteDB. Обновите пробы, сохранив их рабочие каталоги. При запуске проба импортирует `JobResult.json` в `results.db` одной транзакцией; исходный снимок удалится, когда съёмник подтвердит все импортированные записи.
3. Установите отдельный пакет `twamp-collector`. Укажите `Configurator:Url` и перенесите подключение к ClickHouse в настройки съёмника. Для `ClickHouse:SpoolPath` укажите **абсолютный путь к прежнему буферу** либо скопируйте его целиком при остановленных службах. У учётной записи съёмника должны быть права записи в этот каталог. Съёмник подхватит прежние `current.ndjson` и `seg-*.ndjson`, включая результаты, уже подтверждённые старым сервером. Для существующей таблицы используются `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` и `INSERT`.
4. В конфигураторе укажите `Collector:Url`. Для разных машин настройте адрес прослушивания `Urls` съёмника и общий `Auth:ApiKey`. Запустите службы, откройте «Хранилище» и проверьте появление строк в целевой таблице. Новые архивы замеров на пробе не создаются. Старые ZIP остаются историческими файлами.

### Регистрация и распределение проб

В настройках съёмника задайте уникальный `Collector:Id` из строчных латинских букв, цифр, дефисов или подчёркиваний. Для прежнего единственного съёмника предусмотрен `default`, а существующие записи проб автоматически относятся к нему. При нескольких экземплярах настройте каждому собственный каталог буфера.

На вкладке «Статус проб» введите HTTP(S)-адрес запущенного съёмника и нажмите «Зарегистрировать». Конфигуратор проверяет `/identity` с общим ключом и сохраняет адрес в LiteDB. Повторная регистрация того же ID обновляет адрес. Затем опросите пробу и выберите съёмник при подтверждении. У зарегистрированной пробы назначение меняется в столбце «Съёмник». В «Хранилище» и «Отчёте» выберите нужный экземпляр.

Перед ручным переносом пробы на другой съёмник дождитесь подтверждения текущих пачек прежним экземпляром. При переключении во время сбоя возможна повторная доставка, поэтому при работе с общей историей используйте одну целевую таблицу ClickHouse.

Для разработки запустите в отдельных терминалах `dotnet run --project SPI.Twamp.Server --no-launch-profile` и `dotnet run --project SPI.Twamp.Collector --no-launch-profile`, затем пробу с её собственным `appsettings.json`. Съёмнику нужен доступный ClickHouse.

## Разработка

```
SPI.TWamp.slnx              — решение (.NET 11)
├── go-probe/               — проба (Go): один бинарник, twampy и файлы установки
├── SPI.Twamp.Server/       — сервер (ASP.NET Core, LiteDB)
└── SPI.Twamp.Tests/        — юнит-тесты (xUnit)
```

Сборка и тесты:

```bash
dotnet build SPI.TWamp.slnx -c Release
dotnet test --project SPI.Twamp.Tests/SPI.Twamp.Tests.csproj -c Release
```

Тестами покрыты: разбор длительностей шаблонов (`TimeSpec`), разбор строк файла маршрутизаторов, детерминированные идентификаторы задач, парсер вывода `twping`, **парсер вывода `twampy` и его сходимость по значениям с twping** (`TwampyParserTests`), слияние задач в реестре пробы.

CI: GitHub Actions ([.github/workflows/build.yml](../.github/workflows/build.yml)) — сборка решения и тесты .NET **плюс** gofmt/vet/тесты/сборка Go-пробы (linux и windows) на каждый push/PR в `main`. У Go-пробы свои юнит-тесты (`go-probe/*_test.go`): контракты JSON (PascalCase/числовые enum от сервера, camelCase-ответы), конфигурация с BOM, ACK-доставка с повторной выдачей, слияние задач, очистка сторожем.

### Релизы

Пуш тега `v*` (например `v1.2.0`) запускает [.github/workflows/release.yml](../.github/workflows/release.yml):
собираются **шесть архивов** (в каждом — папка приложения целиком) и публикуются в GitHub Release.
Версия из тега прошивается во все сборки: .NET-приложения получают её в `AssemblyVersion`
(локальные сборки — версию из `Directory.Build.props`), Go-проба — через `ldflags`;
она видна в списке проб на сервере.

| Архив | Вариант | Требования на хосте |
|---|---|---|
| `twamp-server-*-framework.tar.gz` | сервер, маленький (~7 МБ) | установленный .NET 11 Runtime (ASP.NET Core) |
| `twamp-server-*-selfcontained.tar.gz` | сервер, самодостаточный (один исполняемый файл со всеми библиотеками) | нет — распаковал и запустил |
| `twamp-probe-go-*-linux-x64.tar.gz` | **проба** (Go) для Linux — один статический бинарник ~6 МБ | нет; для режима TWampy — Python 3.8+ |
| `twamp-probe-go-*-windows-x64.zip` | **проба** (Go) для Windows | нет; для режима TWampy — Python 3.8+ |

Выпуск релиза:

```bash
git tag v1.2.0 && git push origin v1.2.0
```

Ручной запуск workflow (без тега) собирает те же архивы как артефакты сборки.
Runtime-файлы состояния (`TaskInfo.json`, `results.db`, `JobResult.json`, `Base test.csv`) в дистрибутивы не попадают.

Стиль кода: clean-архитектура (слои с интерфейсами, тонкие контроллеры), XML-документация и комментарии — **на русском языке**.

## Обновление

Установка и обновление — **один и тот же скрипт**, тот, что лежит в архиве:
`install.sh` для Linux, `install.cmd` для Windows. Первый запуск ставит,
каждый следующий обновляет; отличать их самому не нужно — скрипт сам скажет,
что делает.

Что происходит при обновлении:

| | Что с ним |
|---|---|
| исполняемые файлы, `twampy/`, `twping` | заменяются на новые |
| `appsettings.json` | **дополняется**: ваши значения остаются, новые ключи добавляются рядом, установщик их перечисляет |
| база `TWamp.db`, буфер `spool/` (сервер) | не трогаются |
| настройки ядра `99-twamp-probe.conf` (проба) | применяются заново |
| служба | останавливается на время замены файлов и запускается снова |

Слияние настроек делает само приложение (`--merge-config`), а не скрипт:
разбирать JSON в shell нечем — `jq` на минимальной системе может не оказаться.
Ничего не удаляется: настройка, которой в новой версии больше нет, безвредна и
пригодится при откате. Испорченный `appsettings.json` (неверный JSON)
установщик не тронет — остановится с ошибкой. Порядок ключей, текст значений
и права на файл при слиянии сохраняются.

Особый случай — **комментарии** в серверном `appsettings.json` (.NET их
допускает). Сохранить их при переписывании сервер не умеет, поэтому такой
файл он не трогает вовсе: установщик перечислит новые ключи и попросит
добавить их вручную. У пробы (Go) комментарии в JSON не поддерживаются и
вопроса не возникает.

Значения по умолчанию из новой версии **не навязываются**: если у вас
`Probe:MaxParallel = 500`, он таким и останется. Смотреть за изменившимися
рекомендациями стоит в [конфигурации](configuration.md) — например,
`Probe:PortRange` и `ip_local_port_range` в версии 1.19 разведены неспроста.

- Пробу и сервер обновляйте **согласованно**: контракт обмена результатами (пачки с подтверждением) несовместим со старыми версиями второй стороны.
- Версия каждой пробы видна на странице статуса — после раскатки легко найти отставшие.
- Прежние сегменты уже принятых измерений переносит съёмник. Оставляйте исходный буфер до проверки строк в целевой таблице.
